# Admission control

When `[admission] enabled = true`, every completion request must be admitted
before it is sent to a provider. Admission enforces three limits per gateway key,
shared by every gateway instance through one Redis server:

- **requests per minute**, a token bucket of requests;
- **tokens per minute**, a token bucket of model tokens, charged by reservation;
- **concurrent requests**, a count of active leases.

Requests that fail validation, name an unknown alias, or are rejected by the
provider adapter's capability checks never reach admission and consume nothing.

## Identity and key layout

Limits are keyed by the principal ID: `key-` followed by the first 12 hex
characters of the SHA-256 digest of the gateway key. It is derived from the
authenticated key, so callers cannot choose it, and it reveals nothing about the
key. Per-key overrides in `[admission.key_limits]` use the same ID, which also
appears in logs.

All state for one key shares a Redis Cluster hash tag:

```text
agw:v1:{key-0123456789ab}:requests               hash   token bucket
agw:v1:{key-0123456789ab}:tokens                 hash   token bucket
agw:v1:{key-0123456789ab}:leases                 zset   reservation ID -> lease expiry (ms)
agw:v1:{key-0123456789ab}:reservation:<id>       hash   state, reserved and charged tokens
```

Reservation IDs are 128-bit random values generated by the gateway. They are never
accepted from clients and authorize nothing.

## Token buckets

Each bucket stores a balance and the time it was last updated. On each admission
the balance is refilled by `elapsed_ms * rate_per_minute / 60000`, capped at the
bucket capacity (the configured burst). A request costs one request token; a
reservation costs its reserved number of model tokens. A bucket that would be full
is indistinguishable from an absent one, so each bucket key expires when it would
have refilled completely and idle keys use no memory.

Burst behaviour: after a quiet period a key may make `request_burst` requests at
once; after that, requests are admitted at `requests_per_minute`. Rejections carry
`Retry-After`, rounded up to whole seconds, computed from the missing balance and
the refill rate. Concurrency rejections have no `Retry-After`, because the time at
which a running request finishes is not known.

Time comes from the Redis server (`TIME`), not from gateway hosts. If the server
clock moves backwards, for example after failing over to a replica with a slower
clock, the elapsed time is treated as zero and no tokens are refilled.

## Token reservations

The provider reports token usage only after a response completes, so admission
reserves an upper estimate first and settles it afterwards.

```text
reserved = estimated input tokens + output allowance
```

- **Estimated input tokens**: UTF-8 bytes of each message divided by 3 and rounded
  up, plus 4 tokens per message and 3 per request (`gateway.admission.tokens`).
  This is a heuristic, not the provider's tokenizer. It over-estimates typical
  English text and is close for scripts that use three UTF-8 bytes per character;
  it can under-estimate unusual input.
- **Output allowance**: the request's `max_tokens`, else the model's
  `default_max_tokens`, else its `max_output_tokens`. The allowance is always sent
  to the provider as `max_tokens`, so the provider enforces the bound that was
  reserved. If a key has a token limit and no allowance can be determined, the
  request is rejected with `max_tokens_required`. A reservation larger than the
  bucket capacity can never be admitted and is rejected with
  `token_reservation_exceeds_limit`.

## Atomic admission

One Lua script, `admit`, runs all checks and then all updates:

1. If a record for this reservation ID exists, return its result unchanged
   (`released` tombstones refuse; anything else is reported as admitted).
2. Remove expired leases.
3. Compute the refilled request and token balances; check request >= 1, token
   balance >= reservation, and active leases < concurrency limit.
4. If any check fails, return the reason and the refill delay. Nothing is written,
   so a token rejection does not consume a request token and a concurrency
   rejection consumes neither.
5. Otherwise deduct both buckets, add the lease, and write the reservation record
   in state `admitted`.

Redis runs a script without interleaving other commands, so concurrent admissions
from any number of gateway instances are serialized per server.

## Leases

A lease lasts for the request deadline plus `lease_grace_seconds`. A request cannot
run past its deadline, so a lease cannot expire while its request is active, and no
renewal is needed. If a gateway process dies, its leases expire on their own and
the next admission for that key removes them.

## Settlement

When a request finishes, for any reason, the `settle` script runs once:

1. Remove the lease. This is idempotent.
2. If the reservation record is missing, write a `released` tombstone and stop.
   The admission either never committed or its record has expired. Either way
   nothing is refunded, and an admission with this ID still in flight cannot commit
   afterwards.
3. If the record is not `admitted`, stop. It was already settled.
4. Replace the reservation with the tokens charged: the bucket balance becomes
   `refilled balance + reserved - charged`, clamped to `[-capacity, capacity]`.
5. Mark the record `settled` and keep it for the lease lifetime plus
   `reservation_retention_seconds`.

Charges per provider attempt:

| Attempt outcome | Charged |
| --- | --- |
| Provider reported usage | the reported total |
| Completed without usage, stream interrupted, read timeout, client cancelled | the full reservation |
| Connection not established, or the provider returned an error status (other than 408/504) | nothing |

The usage status of a settlement is `observed` when every charged attempt reported
usage, `unknown` when any attempt was charged its full reservation, and `none`
when nothing was charged.

Usage above the reservation becomes debt: the balance goes negative and later
admissions for the key wait until it refills. Debt is capped at one bucket
capacity. Request tokens are never refunded: a request that was admitted counts
against the request limit whatever its outcome.

Settlement runs in a task shielded from cancellation, so a client disconnect or
deadline expiry during settlement does not abandon it.

## Failure policy

Redis is part of the admission decision. With admission enabled:

- Any Redis error or timeout during admission refuses the request with 503
  `admission_unavailable`. There is no local fallback.
- Every Redis call is bounded by `redis_operation_timeout_seconds` and by the
  remaining request deadline. Connections come from a bounded pool
  (`redis_max_connections`, waiting at most `redis_pool_timeout_seconds`).
- redis-py's automatic command retries are disabled. Each request makes at most
  one admission call.
- `/health/ready` pings Redis and returns 503 when it does not answer.

**Lost replies.** If the admission call fails or is cancelled after the command
may have reached Redis, the gateway cannot tell whether it committed. It refuses
the request (or propagates the cancellation) and settles the reservation with zero
tokens in a background task. Settlement is idempotent, and if it happens to run
before the delayed admission, its tombstone makes that admission fail. So the
lease is released whichever order Redis sees the commands in, and any reserved
tokens are refunded. A request token may stay consumed.

If settlement itself fails (`reservation unresolved` in the logs, and the
`gateway_reservations_settled_total{outcome="failed"}` metric), the lease expires
after its TTL and the reserved tokens stay charged: the gateway errs towards
under-admission.

**Restart.** Requests made while Redis is down are refused. Pooled connections
that the server closed are detected when next checked out of the pool and
re-established, so admission resumes with the first request after Redis is back.

## Consistency and durability assumptions

- **One logical Redis primary.** All admission state for a key is written by one
  script on one server. Redis Cluster is supported by the key layout, as each key's
  state lives in one slot.
- **No durability guarantee.** If Redis loses data (a restart without persistence,
  or failover to a replica that had not received recent writes), buckets reset to
  full and active leases are forgotten. Until in-flight requests finish, a key may
  then be admitted beyond its limits. Atomic scripts do not change this; it depends
  on the Redis persistence and replication configuration.
- **Token limits are approximate.** Admission is exact with respect to
  reservations, but reservations are estimates, and providers that do not report
  usage are charged the full reservation. Actual provider token consumption per
  minute can be above or below the configured limit.
- **Concurrency is bounded by leases, not by provider work.** A lease is released
  when the gateway stops waiting for a request, even if a provider keeps working on
  an abandoned request.

## Operational notes

- Memory per active key is a few small hashes plus one reservation record per
  request kept for the lease lifetime plus retention. As a rough bound, the number
  of records for a key is its request rate times
  `(deadline + lease_grace_seconds + reservation_retention_seconds)` in minutes.
  Keys exist only for authenticated principals, so unauthenticated traffic cannot
  create state.
- `gateway_admission_decisions_total{outcome}`, `gateway_admission_duration_seconds`,
  `gateway_reservations_settled_total{outcome}`, `gateway_reserved_tokens_total`,
  `gateway_charged_tokens_total{usage}`, and `gateway_redis_errors_total{operation}`
  describe admission behaviour. The `admission decision`, `reservation settled`,
  and `reservation unresolved` log events carry the principal and reservation IDs.
